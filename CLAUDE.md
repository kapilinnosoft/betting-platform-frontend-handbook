# Working rules for this handbook

This repository holds the canonical Markdown handbook plus its Next.js documentation portal in `website/`. Betting application source lives in other repositories and is **read-only**. The portal renders this handbook; it is not a betting application.

## Before any work
1. Read `inventory/documentation-progress.md` and `inventory/open-questions.md`.
2. Check which module or phase is approved. Phase 1 is the User Panel, and each module needs explicit approval before work starts on it.

## Rules
- Never modify application source or configuration in the reference repositories. Portal code and configuration inside `website/` may be changed for portal work approved by the user.
- Do not install dependencies for handbook analysis. For an explicitly approved portal task, install only dependencies required by the existing template and portal feature.
- Markdown documents and inventories remain the technical source of truth. Do not duplicate their content in React constants or components; render the Markdown or derive structured views from the inventories.
- The portal is generic: do not show specific project, company, client, source-repository or organization names. Preserve source paths needed for engineering traceability, but redact project labels at presentation time.
- Never invent endpoints, fields, intervals, formulas or business rules. Use the labels in `README.md`.
- Every technical claim cites `repo:path:line` plus the function or component name.
- Keep rsplay and vishnu7 **frontend** behaviour in separate sections. Similar names do not mean identical behaviour (e.g. rsplay `placeBet` and vishnu7 `betPlace`).
- Backends share one template (team confirmation, Q-12). A backend contract confirmed in one repo may be cited for the other's common endpoints as `INFERRED (shared backend template)`. Brand-specific modules are never assumed.
- 1 s and 2 s polling and `t: Date.now()` cache-busting are intentional (Q-03, Q-05, Q-06). Cache-busting exists because odds and live data must reach the user immediately. Document them as design intent, not as defects.
- Other team-confirmed intent, not defects: vishnu7 `/home` lists only cricket (Q-18); vishnu7 casino filters are lower-cased because the backend matches lower-case values (Q-25). vishnu7 `ARCHITECTURE.md` was copied from another project and is ignored (Q-11). rsplay guest home listing dropping forecast-market races is platform-specific (Q-16). Scorecard and Live TV URLs are fetched once per page by design: they open a direct stream, and toggling TV off/on reloads it (Q-31). `/bet/place` `position` is optional; `acceptOddsChange` is not yet used by the backend but is kept on purpose so that, once enabled, a bet whose odds change during placement goes through at the updated odds (Q-22). rsplay account statement opening/closing balance taken from the current page is platform-specific (Q-27). `GET /bet/profit-loss` returns both `filteredProfitLoss` and `totalProfitLossAllSports` (Q-29).
- When an endpoint name is defined twice for the same URL, document only the definition in use, meaning the one injected first by import order (Q-01). Mark the other as "not in use".
- Team-confirmed code defects are listed under "Confirmed frontend fixes" in `inventory/open-questions.md`. Add new ones there when the team confirms them.
- Document an API in full once, in its module's `api-inventory.md`. Other pages link to it.
- Never include secrets, tokens, real stream URLs or real user data. Sanitise examples.
- After each module, update `inventory/documentation-progress.md`, `inventory/api-inventory.md`, `inventory/polling-and-frequency-inventory.md` and `inventory/open-questions.md`. Then stop for approval.
